# AI 教育后端项目改进目标与验收标准

> 文档状态：实施规格（尚未代表功能已完成）  
> 最后更新：2026-09-01  
> 适用项目：`fctts-main5`  
> 参考项目：[shareAI-lab/learn-claude-code](https://github.com/shareAI-lab/learn-claude-code)

## 1. 文档用途

本文档是后续项目改造、代码实现、测试、压测和答辩准备的单一事实来源。其他对话开始工作前，应先阅读本文档，并遵循以下原则：

1. 未经测试的数据不得写成已取得的结果。
2. 每项优化必须保留优化前基线、修改内容、优化后结果和适用边界。
3. 所有性能数字必须能够关联到测试环境、压测脚本、原始结果和 Git commit。
4. 优先完成一个可验证的业务闭环，不为丰富技术栈盲目引入中间件。
5. MySQL 是业务数据的唯一真源；Redis 用于缓存、短期状态和并发协调，不取代业务持久化。

## 2. 总体目标

将项目从“调用大模型和语音服务的 Spring Boot 功能集合”升级为：

> 一个具备 Agent Harness、上下文管理、质量评估、Redis 工程实践、并发隔离、故障降级和可重复性能验证的 AI 教育后端。

最终项目必须同时证明以下能力：

- AI 与实际教育业务融合，而非仅封装大模型接口。
- Agent Loop、工具调用、上下文压缩、记忆、权限和目标检查等 Harness 能力。
- Redis 在分布式会话、原子状态推进和 MySQL 查询缓存中的真实价值。
- MySQL 与 Redis 最终一致性设计及异常补偿能力。
- 对阻塞、并发、线程池、背压、长任务异步化的工程理解。
- 通过自动化测试、故障注入和压测量化证明优化效果。
- 能够清晰解释设计选择、替代方案、代价和边界。

## 3. 范围与非目标

### 3.1 本轮核心范围

选择“AI 学习助理”作为唯一核心 Agent 业务闭环：

```text
用户提出学习目标
  -> 查询相关课件
  -> 获取历史口语成绩
  -> 识别薄弱知识点
  -> 生成练习或学习计划
  -> 保存学习笔记或任务
  -> 检查目标是否完成
```

第一版至少提供以下五个原子业务工具：

1. 查询课件内容。
2. 查询用户历史口语成绩。
3. 查询用户画像或薄弱项。
4. 生成练习内容。
5. 保存学习笔记或学习任务。

### 3.2 当前非目标

在核心闭环完成并通过验收前，不主动引入：

- 微服务拆分。
- Kafka 等消息中间件（除非可靠补偿确有需要并有证据）。
- Elasticsearch。
- 向量数据库。
- Kubernetes。
- 多 Agent 团队。
- 复杂可视化工作流编排。

## 4. 分阶段实施目标

### 阶段 A：基线、可观测性和压测环境

目标：先测量现状，再进行优化。

交付物：

- Actuator 与 Micrometer 指标。
- HTTP、模型、工具、Redis、MySQL、线程池和后台任务指标。
- WireMock 或等价 Mock 上游，可模拟固定延迟、429、500、超时、空响应和非法 JSON。
- k6、Gatling 或 JMeter 压测脚本。
- `docs/performance-report.md` 初始基线报告。
- 原始压测结果目录及运行说明。

### 阶段 B：最小 Agent Harness

目标：实现模型决策、工具执行、结果回填和目标闭环，而不是固定 Prompt 流水线。

建议模块：

```text
agent/
  AgentLoopService
  AgentSession
  AgentMessage
  ToolCall
  ToolResult
  ToolRegistry
  AgentPermissionService
  GoalEvaluator

agent/tool/
  SearchCoursewareTool
  GetSpeakingHistoryTool
  GetUserProfileTool
  GenerateExerciseTool
  SaveStudyNoteTool

agent/context/
  ContextAssembler
  ContextCompactor
  TokenBudgetPolicy
```

### 阶段 C：上下文、记忆和评估

目标：建立可预算、可压缩、可追踪、用户隔离的上下文体系。

上下文至少包含：

- 系统规则。
- 当前学习任务。
- 用户画像。
- 长期薄弱项。
- 最近有效对话。
- 相关课件片段。
- 工具执行结果。
- 输出格式约束。
- Token 预算。

同时建立固定版本的 AI 评估集和自动回归入口。

### 阶段 D：Redis 会话和缓存一致性

目标：把 Redis 做成可解释、可测试的实际业务能力。

两个重点场景：

1. 使用 Redis Hash、TTL 和 Lua 脚本保存并原子推进 Agent/对话会话。
2. 对高频音色或课件查询使用 Cache Aside，MySQL 为唯一数据真源。

### 阶段 E：并发隔离、韧性和异步任务

目标：避免外部 AI、ASR、TTS 或文件处理耗尽 Web 请求线程。

至少区分：

- LLM 调用专用有界线程池或 Bulkhead。
- ASR/TTS 工作负载。
- PPT、视频、长音频等后台任务。

长任务使用以下协议：

```text
提交任务 -> 返回 taskId -> 后台处理 -> 查询状态或推送结果
```

### 阶段 F：报告、答辩和最终收口

目标：形成可以复现、可以讲解、可以追问的完整工程证据链。

## 5. 验收标准

以下条目为硬性验收门槛，除非明确标记为“建议目标”。

### 5.1 Agent Harness

- [ ] 支持模型调用、工具调用、工具结果回填、继续推理和正常结束。
- [ ] 新增工具只需要实现统一接口并注册，不修改 Agent 主循环。
- [ ] 至少接入 5 个真实教育业务工具。
- [ ] 支持最大 8 步循环限制。
- [ ] 支持总体 deadline 和 Token/成本预算。
- [ ] Goal Evaluator 可以区分完成、未完成、无法完成和超限。
- [ ] 所有写操作经过权限检查；跨用户越权执行成功数必须为 0。
- [ ] 每次运行保存模型调用、工具调用、耗时、状态和错误轨迹。
- [ ] 固定评估集不少于 100 条。
- [ ] 任务完成率不低于 90%。
- [ ] 工具选择正确率不低于 95%。
- [ ] 工具参数正确率不低于 95%。
- [ ] 评估集中死循环数为 0。

### 5.2 上下文设计

- [ ] `system`、`user`、`assistant`、`tool` 消息角色分离，不再拼成一个字符串。
- [ ] 每类上下文有明确 Token 预算，总输入不会无限增长。
- [ ] 超过预算时先裁剪冗余工具输出，再压缩历史消息。
- [ ] 工具结果保留来源和调用标识。
- [ ] 每次模型调用记录 Prompt 版本和模型版本。
- [ ] 50 轮连续对话后仍可正常完成任务。
- [ ] 上下文压缩关键事实保留率不低于 95%。
- [ ] 与完整历史直接拼接相比，Token 使用量降低至少 40%。
- [ ] 用户 A 的上下文、记忆和工具结果不得进入用户 B 的会话。

### 5.3 Redis 分布式会话

必须使用 Testcontainers 或 Docker 中的真实 Redis 验收，不能只使用 Mock。

- [ ] 会话能够跨两个应用实例读取。
- [ ] TTL 到期后会话自动失效。
- [ ] 同一会话并发推进 100 次，不发生丢失更新。
- [ ] 最终轮次值与成功请求数一致。
- [ ] Lua 脚本原子完成所有权校验、轮次推进和 TTL 刷新。
- [ ] 其他用户推进会话时 100% 被拒绝。
- [ ] 重复请求有明确幂等策略。
- [ ] Redis 不可用时按设计快速失败或降级，不长时间阻塞。
- [ ] Redis 连接超时和命令超时均有明确配置。

### 5.4 MySQL 与 Redis 缓存一致性

采用 Cache Aside，MySQL 为唯一数据真源。

- [ ] 缓存未命中时读取 MySQL 并回填 Redis。
- [ ] MySQL 事务提交成功后删除对应缓存。
- [ ] MySQL 事务回滚时不能产生新的缓存状态。
- [ ] 新增、更新、删除成功后立即查询能够得到最新数据。
- [ ] Redis 删除失败会进入可观测的重试或补偿流程。
- [ ] 补偿成功时间不超过 60 秒。
- [ ] Redis 宕机时读取请求能够回源 MySQL。
- [ ] 缓存 Key 包含必要的用户和业务维度。
- [ ] TTL 具有随机抖动，避免集中失效。
- [ ] 90% 重复读取负载下，缓存命中率不低于 85%。
- [ ] 相比无缓存基线，MySQL 查询次数降低至少 80%。
- [ ] 缓存接口 p95 相比无缓存基线降低至少 30%。
- [ ] 100 个并发缓存未命中时，不能产生 100 次相同 MySQL 查询。

### 5.5 线程池与并发隔离

- [ ] LLM、ASR/TTS、文件后台任务之间有明确隔离策略。
- [ ] 所有业务线程池使用有界队列。
- [ ] 禁止使用无界线程池或无界任务队列。
- [ ] 文档说明 core、max、queue 和拒绝策略的依据。
- [ ] 至少保留两组线程池参数的压测对比。
- [ ] 每个线程池暴露活跃线程、队列长度、完成数和拒绝数。
- [ ] 一个外部服务阻塞时，普通数据库查询仍然可用。
- [ ] 队列满时能够快速拒绝或降级，不无限排队。
- [ ] 应用关闭时能够优雅停止任务。
- [ ] 30 分钟稳定性压测中无线程持续增长、死锁或 OOM。

### 5.6 长任务异步化

- [ ] PPT、视频、长音频和长文本处理采用异步任务协议。
- [ ] 提交接口返回 HTTP 202 和有效 `taskId`。
- [ ] 提交接口在 100 并发下 p95 不高于 200ms。
- [ ] 任务状态至少包含等待、运行、成功、失败和取消。
- [ ] 重复提交支持幂等 Key。
- [ ] 用户只能查询和取消自己的任务。
- [ ] 后台任务失败能够返回可诊断的错误原因。
- [ ] 应用重启后，已持久化任务能够恢复或明确失败。
- [ ] 任务结果和临时文件具有过期清理机制。

### 5.7 外部 AI 服务韧性

通过 Mock 上游覆盖固定 2 秒响应、429、500、连接超时、读取超时、空响应和非法 JSON。

- [ ] 连接超时、读取超时和总体 deadline 均有配置。
- [ ] 重试不超过 2 次，仅重试可重试且幂等的请求。
- [ ] 429 使用 `Retry-After` 或退避策略。
- [ ] 连续故障能够触发熔断。
- [ ] 熔断期间请求快速失败，不继续占用工作线程。
- [ ] 单个模型服务故障不会拖垮普通业务接口。
- [ ] 降级响应明确标记 `source=local` 或 `source=fallback`。
- [ ] 上游恢复后熔断器能够半开并自动恢复。

### 5.8 性能验收

#### 固定口径

- 同一硬件、JVM 参数、数据规模、MySQL 和 Redis 版本。
- Mock 模型固定延迟 2 秒。
- 每轮预热 2 分钟，稳定压测 10 分钟，至少重复 3 次。
- 使用三次结果的中位数进行比较。
- 报告记录 Git commit、运行命令和原始结果路径。

#### 建议起始 SLO

| 接口类型 | 100 并发下验收标准 |
| --- | --- |
| Redis 缓存查询 | p95 不高于 100ms |
| 普通 MySQL 查询 | p95 不高于 300ms |
| Mock AI 同步接口 | 后端额外开销 p95 不高于 300ms，即总 p95 不高于 2.3s |
| 异步任务提交 | p95 不高于 200ms |
| Redis 会话推进 | p95 不高于 200ms |
| 稳定压测错误率 | 不高于 0.5% |

真实模型延迟受供应商影响，不作为固定通过阈值，但必须记录：

- [ ] 首 Token p50 和 p95。
- [ ] 总响应 p50、p95 和 p99。
- [ ] 输入、输出和总 Token 数。
- [ ] 供应商错误率、超时率和降级率。
- [ ] 单请求估算成本。

### 5.9 AI 质量评估

- [ ] 评估集覆盖工具选择、参数抽取、课件总结、口语反馈、上下文压缩、异常和权限。
- [ ] 修改 Prompt、模型、工具或上下文后可自动回归。
- [ ] 结构化输出格式合规率不低于 98%。
- [ ] 事实一致性通过率不低于 90%。
- [ ] 人工抽样不少于 30 条，平均评分不低于 4/5。
- [ ] 新版本核心指标不得低于基线超过 2 个百分点。
- [ ] 评估结果记录模型版本、Prompt 版本、数据集版本和 Git commit。

### 5.10 可观测性

每个请求使用统一 `traceId` 串联：

```text
HTTP -> Agent Loop -> 模型调用 -> 工具调用 -> Redis/MySQL -> 最终响应
```

- [ ] 可查看 HTTP p50、p95 和 p99。
- [ ] 可查看模型调用延迟、Token 和失败类型。
- [ ] 可查看 Agent 平均执行步数和目标完成状态。
- [ ] 可查看工具调用成功率和耗时。
- [ ] 可查看 Redis 命中率和命令延迟。
- [ ] 可查看 MySQL 连接池和慢查询。
- [ ] 可查看线程池活跃数、队列长度和拒绝数。
- [ ] 可查看熔断、限流、降级和后台任务积压数量。
- [ ] 日志不得包含 API Key、密码、完整 Token 或不必要的用户敏感内容。

### 5.11 自动化测试与 CI

- [ ] `mvn verify` 一条命令能够完成构建和普通测试。
- [ ] 核心模块行覆盖率不低于 80%。
- [ ] 核心并发和一致性分支覆盖率不低于 70%。
- [ ] MySQL 和 Redis 集成测试使用可重复环境。
- [ ] 普通测试不依赖真实 Moonshot 服务。
- [ ] 所有测试连续执行 3 次无随机失败。
- [ ] 仓库中不存在真实密钥和环境密码。
- [ ] CI 测试失败时禁止合并。

必须存在以下测试：

- [ ] Agent 循环正常结束和超限结束测试。
- [ ] 上下文压缩和用户隔离测试。
- [ ] Redis Lua 并发测试。
- [ ] MySQL 事务回滚与缓存一致性测试。
- [ ] 缓存删除失败补偿测试。
- [ ] 线程池队列满和拒绝策略测试。
- [ ] 模型超时、429、500、熔断和恢复测试。
- [ ] 用户数据和工具权限测试。

## 10. 答辩必答问题

项目负责人必须能够独立回答：

1. 为什么该业务需要 Agent，而不是普通固定接口？
2. Harness 提供了哪些模型本身不负责的能力？
3. 为什么引入 Redis？它分别解决了什么业务问题？
4. Redis 用作缓存和用作会话状态有什么差别？
5. MySQL 与 Redis 为什么选择最终一致，异常窗口如何补偿？
6. 为什么线程池需要隔离，队列为什么必须有界？
7. 为什么增加线程不能直接解决外部模型延迟？
8. 性能瓶颈是如何定位的？
9. 优化前后数据有什么变化，如何保证测试公平？
10. 当前方案的代价和失效边界是什么？
11. 如果流量增加 10 倍，下一步优先优化哪里？
